## Where they disagree

**What "faster" is compared with.** The launch thread says 20-200x and 40-400x. The blog says 193.6x and 444.6x are the high end of four workflows against an adapter-wrapped LLM, and that a single side-by-side used a short state that favored Jev. Stefan says one question is about 1.5–3x against a small chat model, and the large factors come from deleting or batching calls. Edward's invoice says the judgment layer was $0.0025 against $0.37 of search. The cheap call does not make the workflow cheap if retrieval dominates. Navin repeats 100x and 10-100x as the reason to care, and then says speed does not matter if the answers are wrong.

**Whether typed output can be wrong.** The launch blog says Jev can't hallucinate, and then says the 0% figure is schema matching, not a measured error rate. Navin says that reading is false: a yes/no can still be the wrong yes/no. The jaggedness page lists failures that are wrong answers inside a valid type. Glean's ranker gave the same score to most candidates, which is a typed answer that did not rank. Zhaorun says a typed model followed injected instructions.

**Whether to replace a production ranker.** Rox says they are shipping Jev-Score. Glean says Jev is a baseline and the ties had to be broken with the old order. Crown says matches per 200 candidates rose 30.64% and the writeup is not out. These are three authors and three claims. They are not one result.

**Where the threshold sits.** The Noul page says 0.5 when yes and no cost the same, higher when a false yes is expensive. Edward priced a false escalation at $0.14 and a miss as silence, and kept 0.5 because silence was worse. At 0.7 he lost the Gulf briefing. The Qwen judge, on his numbers, wandered across that line. Glean's citation check is a different stability result: Jev moved less than GPT-5.6 Luna. Xia Chen's unanswered point is that Edward did not replay frozen inputs, so some of the wander could be retrieval, not the judge.

**Who should route a model.** Theo, @theo, post 2103614549006156146, 25 September 2026, likes 815, reposts 26, bookmarks 158, views 86965, wrote that Jev categorizes and does not think, so it cannot know from a prompt whether "port this to Rust" is a hundred lines or a million. That post is too short to be its own file. Keel agrees in practice: the host filters routes it can actually run, and a pinned route is not overridden. The OpenRouter announcement TypeSafe amplified (25 September, post 2103612889655353346) sells Jev as the router for every call. Theo is the objection to that product. No written router architecture was recovered, only the announcement and a video.

**Open weights.** Glean: fine-tuned Laya beat zero-shot Jev on one classification (74.5% against 66.8%) after a few hours of local training, and base Laya was at 35.9%. Navin: on his email task Laya's context was too small, and after he shortened the mail, Laya still did worse. He does not print the rate. John Kim: a Tetris speed win for local Laya may be network latency, and a task only needs to clear a bar. Keel's build did not call hosted Jev during the release check. Local Laya is the default there.

**What a game demo proves.** John Kim: without a real game state and a bot that can already act, Jev is not playing. The launch blog's Doom note says the same thing from the other side: structured text state, not pixels, and a non-AI bot could play better. The blog still presents the demo as the use case.

**Shell approval.** Drew's pattern asks once per command, inside the tool. @RiskAverseTech, post 2105741943326277917, says that misses a helper script: each line looks safe, and the file should be judged at write time. One reply. It is the crack in the pattern, not a writeup.

**Self-improvement.** Keel's improvement-loop proposal says records can be replayed and a person approves the change. The build report and the README say automatic training is not implemented. Do not describe keel as a system that trains itself.
