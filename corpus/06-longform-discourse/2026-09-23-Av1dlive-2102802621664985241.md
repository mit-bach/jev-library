## Before the code: give the decisions a shape

The author wants a coding agent that gets better, and a way to know what changed when it does. The system still needs to choose a model and limit its tools, then check the choice and judge the result. That is where the author puts Jev: give the system a choice you can inspect, then keep enough evidence to judge whether that choice helped.

Each small decision needed three things: named options, a result the code could check, and a record of what happened afterward. An extra model call still has to earn its place.

The article has four parts: how Jev was used as a decision layer, why a coding harness is a useful place for that layer, what was built in keel, and what the decision records make possible for self-improvement and what they do not prove.

A model can suggest the next move. The host still owns the move.

## 01. How Jev was used

In this build, Jev chooses from a list the host prepares. "Host" means the application code around the model. That code decides which options are available before Jev gets a say. Jev returns a typed result the code can check: pick this one, or "I can't choose."

The host prepares the menu. Jev picks from it. The host checks the pick again. A fixed format makes the job: read the result, check it against the current state, accept it or use the fallback.

Two places the selector can act:

1. Choose a route for a new task. When a fresh task has no pinned provider or model, the host prepares eligible provider/model candidates. Jev or local Laya can choose among those candidates, or abstain. A pinned route is one the user already chose. The selector preserves that choice, along with live and resumed sessions. The host removes routes it cannot offer: provider not installed or enabled, model not found, requested reasoning level not supported. The provider still checks its own login when the session starts.

2. Choose the next step inside an embedded DeepSeek loop. Four focus choices: inspect, implement, verify, answer. Each maps to a host-defined tool bundle. The selector returns a focus id. The host finds the allowed tools, then checks them against the current tool definitions before use. "Answer" gets no tools.

These are different from asking Jev to control every coding agent in the app. It does not.

External agents keep their own loops. Keel can host several coding providers through the agent client protocol (ACP). Those providers run their own tool loops. In this build, Jev and Laya do not take over those internals. A listed slash command may just become prompt text for the provider. A description is not an API.

There is also a computer-use decide path. It lets Laya or Jev select a host-prepared, low-risk action id or abstain. The command does not execute desktop actions. Choosing a proposed click and carrying out a click are separate. Jev can select a candidate. It cannot approve a dangerous action. User approval still applies where the app requires it. Model selection does not grant authority, and neither does a high confidence value.

Before applying a choice, the host checks that the action still matches the current task state. If the provider list changed or the route is out of date, the host can reject the action and use a fallback. Inside the DeepSeek loop, the host checks the tool set against current tool definitions and checks the named tool again before running it.

"I can't choose" is a valid result. Define the fallback before you call the selector. Record when it was used, so a fallback is not counted as a selector win.

After the host validates the result and observes the outcome, it can write a decision event or receipt. The records are meant to answer: what were the candidates, did the selector choose or abstain, did validation accept it, did a fallback happen, what tool outcome followed. They are not private chain-of-thought. A model's explanation does not prove why something happened.

## 02. Why put it in a coding harness

The author treats coding as a chain of decisions: which model, inspect or edit, which tools, did the repo change while the decision was in flight, retry or abstain or ask, did the change compile and preserve intent. A wrong choice can cost more than a slow one. The harness holds repository state, providers, tool definitions, permissions, task status, and check results. The model is one part of that system.

A standalone decision demo can show a model choosing between three labels. Inside a harness, the host can answer whether the choices were available, whether the task was new or pinned or already running, whether the tool still existed, whether permission allowed it, and what the tool returned.

Laya and Jev are separate selectors. Normal mode skips selection. The author says core ML is Apple's local model runtime. Jev uses a protected credential already on the machine. This build has no key-entry screen. Local Laya is described as the selector. The coding worker may still call a hosted model.

The author has not demonstrated, in this post, that the extra selector call pays for itself on a coding benchmark. The selector cannot choose a good option the host forgot to offer.

For route selection, the model receives candidate ids. Those ids do not let the model invent a new command or provider. Inside the embedded DeepSeek loop, the selector returns one focus id. The host turns that id into a set of allowed tools, then checks again. The decision layer is replaceable. The caller does not need to trust its prose.

If a selector abstained, show that. If the host rejected a stale action, show that. If the host fell back, record the fallback. Putting a decision layer in a harness does not make every result correct. It does not prove that Jev chose the best model. It does not mean a successful build was caused by the selector.

## 03. What was built

Keel 0.2.0, a local-first Mac coding app. Base: an Avid-derived coding workspace. Language: Rust. Interface: GPUI. Platform: Apple silicon, macOS 15 or later.

The author separates two kinds of work: the application (sessions, providers, tools, local decision modes) and the Jev engineering research material. They are related and they are not the same deliverable.

The design question: where can Jev make a choice that the application can still check?

The route path, in the author's words: a new task arrives without a pinned route. The host reads current provider and model availability. It builds a finite list of eligible candidates. The selected decision mode calls local Laya or hosted Jev, if enabled. The selector returns a candidate id or abstains. The host checks that the choice remains eligible and current. The application starts the route or falls back. A decision record captures what happened. Pinned routes and existing sessions bypass the automatic choice.

Local Laya is the default. Jev is a deliberate opt-in. Normal mode remains available.

Badly formed output, invalid ids, old task details, and abstention each need a clear outcome. The host can reject the choice, use a fallback, or ask the user.

## 04. What "self-improving" should mean

The shipped app records decisions. It does not train itself. It does not automatically train Laya from chat history. It does not silently rewrite its own policy after a failed run. The release does not prove a self-improving agent.

What the records give is the start of a feedback loop. A receipt can become a scenario. A scenario can be replayed against a changed prompt, policy, or model. A human can review the difference.

The author proposes an evaluation design and says measured coding-quality gains are not claimed. Keep the task set and scoring rules fixed. Use a separate task set for the final comparison. Keep the failed examples. Keep a human gate on production changes: candidate construction rules, selector prompts or typed schemas, fallback policy, the local model or hosted route, the tool bundle attached to a focus choice. Keep the old version, replay, inspect regressions, then let a human approve the new baseline.

Where the author would start:

- One choice the host can check.
- Jev can choose among host-prepared options. It does not own the host.
- Laya and Jev are separate modes, not two names for one model.
- Provider-owned inner loops stay provider-owned.
- Selection does not grant permission.
- Records support a future evaluation loop. They do not mean the app trains itself.

Four things to write down if you are building a coding harness: one decision it is allowed to make, the exact choices it can see, what happens when it abstains, and how you will know whether the outcome helped.
